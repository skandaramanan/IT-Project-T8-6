What they asked for

Transcription of the 1940s Wilfred Prest survey cards in a digital form.

These were conducted in a time where the census was paused.

The scale

6,500 historical survey cards

Split into 3 different types for each individual dwelling:

TYPE 1
Handwritten Front
TYPE 2
Handwritten Reverse
TYPE 3
Numeric Encoding
The cards

Three card types for a dwelling

TYPE 1

1  Handwritten front

Household details, plus one column per person, filled in by the interviewer

TYPE 2

2  Handwritten reverse

The interviewer's free-text notes, with nothing on it saying which dwelling it belongs to

TYPE 3

3  Numeric coding card

The answers turned into codes for analysis, and our main extraction target

The pipeline has to sort them, read them and link them back together.

The problem

These cards were stored as PDFs rather than an editable format

As such there were a couple of main requirements that our solution needed:

REQUIREMENT 1

Survey cards should be transcribed into a digital and editable format

REQUIREMENT 2

Human review must be able to edit the extracted fields

REQUIREMENT 3

Reprocessing must be supported

Extraction Pipeline
Extraction pipeline

Segmentation

First, we needed to split the PDFs into images and classify them into their 3 different types.

  • Ruled rows and columns present would result in the card being labelled as a front card
  • Blank cards would be dropped if ink density is < 0.002
  • Otherwise, ink density is used to determine the other 2 cards
    • If ink density is < 3.5%, mark it as a reverse
    • Otherwise, it is a numeric encoding card

What we landed on

What we landed on:

  • Primary model: Gemini Flash-Lite
    • 91.1% accuracy on the benchmark set
    • Up to 500 requests per day with a free API key
  • Secondary model: Qwen2.5-VL
    • 84.6% accuracy on the benchmark set
    • About 12 seconds per card, run locally
Extraction pipeline

Grouping

After extraction, we need a way to group the handwritten fronts to the numeric cards.

  • This is done via dwelling number
  • Each survey front starts a dwelling; numeric cards are then joined by matching these numbers
Extraction pipeline

Schema creation

This step turns our groupings into a structured record

  • Record is a nested format (dwelling → household → persons)
  • These records are identified via MUNICIPALITY-DWELLING-HOUSEHOLD (e.g. 27-0006-01)
Extraction pipeline

Reverse side notes

The interviewer wrote unstructured notes on the backside. The client asked us to capture these too, as they give extra context.

  • Each back card is read by the extractor and attached to the record that was made
  • Back side cards have no clear identifier of what they belong to, so each is placed by position (straight after the front card)
Extraction pipeline

Field confidence scoring

We needed some way of judging how good an extraction answer is. This is done with two models.

  • Every field gets a score from 0 to 1 (calibrated from our benchmark set)
    • Agree – 0.97
    • Disagree – 0.75
    • One blank – 0.74
    • Both blank – 0.97
Extraction pipeline

Validation

Every record that is built is validated against our JSON schema. New results are merged on top of any old ones.

  • This allows the pipeline to be re-run and resumed
  • Keeps reviewers’ corrections after re-runs
Extraction pipeline

Review queue routing

This decides whether a field goes to review. A field is sent to review unless it meets all 3 conditions:

  • Status is ok
  • Confidence is not null
  • Confidence is greater than or equal to 0.97 (both models agree)

  • An older status poll cannot overwrite a newer one
Edge cases we targeted

Leading zeros, the sentinels 997, 998 and 999, void marks, blank-permitted fields and corrected values. Every bug gets a test, and some tests are broken on purpose to prove the code catches these errors.
